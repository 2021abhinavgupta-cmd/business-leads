## 1. Project Overview

A lead-generation and cold-email tool for MMGA Agency: it finds local businesses with weak websites (via Google Maps/Places, or an alternate source per `LEAD_SOURCE`), runs a real technical + visual audit of each site, and drafts a personalized cold email that cites the specific flaws found — reviewed and sent through an inbox-style dashboard rather than blasted automatically. The project's dominant theme across its history (see §13) is **accuracy over cleverness**: nearly every session-scale fix has been about closing a gap where a failed or degraded signal silently produced a confident wrong claim (an invented load time, a "the site is down" email for a site that loads fine, a healthy-looking score that was actually just unmeasured) rather than adding a new capability.

1. **React Frontend**: A sleek, multi-page Dashboard with Top Navigation (Dashboard, Drafts, Costs, History).
2. **FastAPI Backend**: Serves the API and connects the web scrapers, AI analyzers, and persistent storage.
3. **Deep Web Crawling**: Uses `Crawl4AI`, Jina Reader, and Trafilatura to extract deep brand context (Services, About Us) for extreme email personalization.
4. **AI Visual & Technical Auditing**: Captures Playwright desktop screenshots, runs Google Lighthouse CLI for performance/SEO scores, and runs `axe-core` accessibility audits.
5. **Real Visual Bounding Boxes**: Extracts exact `(x,y,w,h)` coordinates from `axe-core` violations and draws a real red box directly on the screenshot for the AI to critique.
6. **Exact Cost Tracking**: Tracks fractional penny costs (to 5 decimal places) for API usage directly in an SQLite database.
7. **Asynchronous Drafts Inbox**: Allows users to run Autopilot, queue up generated AI emails in a Drafts table, and manually review/send them via AWS SES at their leisure.

## 5. Core Modules

### 5.1 `app.py` (FastAPI Server)
- Serves the compiled React frontend `dist/` statically.
- Exposes REST endpoints: `/api/search`, `/api/search-nearby`, `/api/audit`, `/api/audit/progress`, `/api/send`, `/api/check-replies`, `/api/drafts`, `/api/costs`, `/api/history`.
- Plus two deliberately **public, unauthenticated** routes that recipients' mail clients call directly: `/unsubscribe` (RFC 8058 one-click) and `/o/{tracking_id}.gif` (open-tracking pixel). Neither can require an API key or survive a rate-limit rejection — see §8.
- Connects the AI orchestration pipeline to the database and frontend.
- **`/api/audit` refuses to draft anything if Playwright couldn't render the page** (added 2026-08-07, on explicit request — see §8). Returns `{"error": ...}` immediately after `generate_audit_screenshot()` if `html_content` is `None`, before `audit_website`/the AI/`decision_maker` ever run. `main.py:process_single_lead` has the identical check (`"failed_unreachable"` status).
- **`/api/send` refuses to send a flagged or stale draft without an explicit acknowledgement** (added 2026-08-09 — see §8). Looks the draft up by website (`db.get_draft_by_website`) and returns `409` with the specific blockers if it carries unreviewed `review_warnings`, or if it's at least `DRAFT_STALE_DAYS` old. `SendRequest.acknowledge_warnings` defaults to `False` so the gate fails closed; the frontend turns the `409` into a confirm dialog listing the warnings and only retries with `acknowledge_warnings: true` if the human agrees.

### 5.2 `scrapers/website.py` & Deep Crawling
- Uses `Crawl4AI` to extract extremely clean LLM-optimized markdown from the homepage (via a temp `file://` URL — see §8, the documented `raw:html` shortcut doesn't work in 0.9.1).
- Uses `Jina Reader` and `Trafilatura` to deep-crawl context pages (About Us, Services).
- `audit_website()`'s `html is None` branch (Playwright produced nothing after both retries) no longer assumes the site is down — it now fires one plain `httpx` GET before deciding the flaw wording, since a headless-browser failure and an actual outage are different things. See §8.
- **`_pick()`'s CrUX → real-measured → lab priority chain now rejects implausible readings, not just missing ones** (`_is_metric_plausible`, added 2026-08-09) — a value outside `_METRIC_BOUNDS` (e.g. an LCP in the hundreds of thousands of ms, a CLS of 100) falls through to the next source exactly like a `None` already did, instead of being quoted at a lead as fact. See §8.
- Aggregates Lighthouse scores (incl. raw Core Web Vitals — LCP/CLS/TBT, not just the 0-100 category score), PageSpeed fallbacks, security headers (`extruct`), structured data + business-relevant `@type` check (`extruct`), readability (`textstat`), a crawl-based SEO pass (`pyseoanalyzer`), `robots.txt` blanket-disallow check, real alt-text coverage, axe-core violations (desktop + mobile viewport + across every crawled page), broken link data, and business/conversion signals (booking widget, click-to-call/WhatsApp, menu/pricing) — all reconciled into one ranked flaw list by `_build_flaws()` (see §5.6).

### 5.3 `analyzer/lighthouse.py`
- Runs the Google Lighthouse CLI via a Node.js subprocess to gather `performance`, `seo`, `accessibility`, and `best_practices` scores natively. `accessibility` is fetched but not surfaced to the AI prompt — axe-core is the authoritative a11y signal (see §5.6).

### 5.4 `analyzer/visuals.py`
- Headless Playwright script. Homepage screenshot at Desktop (1280x800), **plus** a separate real mobile-viewport (390x844) screenshot — desktop screenshots systematically miss mobile-only problems (overflow, tiny tap targets) that most visitors actually hit.
- **Multi-page crawl**: discovers up to 2 extra internal pages (via `/sitemap.xml` first, falling back to homepage anchor-tag keyword scan) and runs the full check set — axe-core, broken links, font consistency, stretched images, title/meta-description — on each one, not just the homepage. Violations get tagged with their source page (`"(on /about-us page)"`).
- Also runs axe-core **again** at the mobile viewport (WCAG tap-target rules differ from desktop) plus a horizontal-overflow check (`scrollWidth > innerWidth`).
- `page.on("console")` and `page.on("request")` listeners (attached once, persist across every navigation) capture JS console errors and mixed-content (HTTP-on-HTTPS) resource loads.
- **Homepage settle delay is 10s** (bumped from 2s, 2026-08-07) — a fixed wait after the best-effort `networkidle` attempt, specifically to outlast full-screen JS preloaders/intro animations that gate the real homepage content. Extra/mobile pages still use 1.5s (this is a homepage-specific problem, not a general one — see §8). **Adds ~8s to every audit's wall-clock time**, accepted deliberately: this file's whole history is accuracy over speed.
- **Interconnected Red Box Pipeline**:
  1. Runs `axe-core` accessibility audit on every page crawled (desktop + mobile).
  2. Extracts the exact bounding box `(x, y, w, h)` of the most severe UI violation with a valid, **in-viewport** box, across all pages — the attached screenshot is whichever page had the worst one, not always the homepage. See §8 for the viewport-bounds check added 2026-08-07.
  3. Draws a precise red box around the real flaw using `Pillow`.
  4. Passes the `visual_flaw_context` up the chain to the AI prompt.
- Also captures the Playwright navigation's HTTP response headers (`response.headers`, free — reuses the request already being made for the screenshot) for the security-headers check in `website.py`.
- Navigation uses `wait_until="domcontentloaded"`, not `"load"` — see §8 for why this was a real false-"website is down" bug, and for a second, different false-"down" bug fixed 2026-08-07.

### 5.5 `analyzer/ai_audit.py`
- Ingests `company_context` to force extreme outreach personalization, plus Google Maps `Rating`/`Reviews Count` (when available) as a personalization hook ("great reviews but the site doesn't reflect it").
- Takes in the `visual_flaw_context` and is strictly instructed to explicitly mention the red box drawn on the screenshot in the email body; also receives the separate mobile screenshot as a second vision input and is instructed to call out mobile-specific issues explicitly.
- Prompt consumes one pre-ranked `FLAWS DETECTED` section (from `web.flaws`) instead of five separate raw tool-output dumps — see §5.6.
- 4-provider fallback chain: Claude Haiku 4.5 → Gemini 3.5 Flash → GPT-4o-mini → OpenRouter free tier (`google/gemma-4-31b-it:free`, last resort). Gemini and OpenAI use native JSON response mode instead of regex-stripping markdown fences; all 4 providers log their own errors (previously only Gemini did — see §8, that asymmetry hid a broken model ID for a while).
- `enrichment/decision_maker.py`'s `find_decision_maker()` has a 5th, separate last-resort strategy using Anthropic's `web_fetch` server tool (real API cost, ~$0.0008/call, logged to `cost_logs` under `"AI Web Fetch"`) — only tried after the free scraper/LinkedIn-OSINT/email-dork strategies all fail.
- **Visual claims (added 2026-08-09)**: `_build_prompt` only *demands* a design critique when `_has_visual_evidence(web)` is true (a red box was drawn, or the font-consistency/stretched-image check actually fired); with no such evidence it explicitly forbids inventing one. `_verify_visual_claims` then sends the real screenshot plus only the visual-sounding claims to a vision-capable judge (`_call_vision_judge`, same Gemini → Haiku → GPT-4o-mini order and same silent-degradation contract as `_call_judge`) and asks whether each is actually visible in the image. See §8 — this is the claim type every other check is structurally blind to.
- **`review_warnings` (added 2026-08-07, sixth check added 2026-08-09)**: the accuracy safety-net checks (`_check_number_hallucination`, `_verify_source_quotes`, `_verify_grounding`, `_verify_visual_claims`, `_check_spam_trigger_words`, `_check_body_length`) used to only `print()` their findings — real signal nobody was watching, since nothing reads Railway logs while reviewing a draft in the dashboard. Each now also returns its warning text (still prints too); `analyze_lead` collects the non-empty ones into `parsed["review_warnings"]`, which flows through `app.py` → `db.log_draft`/`email_drafts.review_warnings` (JSON-encoded, schema v5) → `/api/drafts` → a visible "Review before sending" banner on the draft card in the frontend. See §8/§9.

### 5.6 `analyzer/flaws.py` — the flaw reconciliation layer
Every audit tool used to dump its raw output into the AI prompt as its own unranked text block, leaving the LLM to figure out what mattered and silently absorb redundant/contradictory signals — most notably, Lighthouse's own `accessibility` score and a separate direct axe-core scan both measured accessibility independently, never compared.

As of 2026-07-10, all tool output gets normalized into a common `Flaw(category, severity, description)` type in `scrapers/website.py:_build_flaws()`, deduplicated/reconciled in code (axe-core wins over Lighthouse's `accessibility` number; the two are never both shown), ranked by severity via `analyzer/flaws.py:rank()`, and handed to the AI as one `FLAWS DETECTED (ranked most severe first)` block. The AI's job shifted from "find the flaws in this raw dump" to "write compelling copy about the 2-3 most severe items on this pre-ranked list" — more consistent results, and the reconciliation logic is visible/testable in code (`test_build_flaws.py`) rather than being an LLM judgment call each time.

Signals feeding into it: Lighthouse/PageSpeed scores + raw Core Web Vitals (LCP/CLS/TBT), CrUX real-user field data (`analyzer/crux.py`, preferred over both lab sources when available — see §5.7/§8), SSL, meta title/description/H1, CTA/contact/testimonials/blog presence, canonical tag, robots `noindex` meta tag + `robots.txt` blanket-disallow, Open Graph tags, structured data + business-relevant schema `@type` (`extruct`), readability (`textstat`), thin content + real SEO warnings (`pyseoanalyzer`), HTML validity (`html-validate`), a second accessibility engine (`pa11y`), security headers, mixed content (HTTP-on-HTTPS), JS console errors, axe-core violations (desktop + mobile viewport, across every crawled page), broken links, viewport meta, favicon, font-family consistency, stretched/blurry images, real alt-text coverage, duplicate title/meta-description across crawled pages, mobile horizontal overflow, and business/conversion signals (booking widget, click-to-call/WhatsApp, menu/pricing) — the last category exists because prior flaws were 100% technical (perf/SEO/a11y/security), and a business owner cares just as much about "can a customer actually convert on this page," see §8.

### 5.7 `emailer/` — sending, deliverability, and engagement measurement
Split across five files, each with one job (see §2 for the list). The dependency direction is one-way: `base_sender.py` knows nothing about SES or Gmail; `ses_sender.py`/`gmail_sender.py` each implement only `_transport_send()` and `check_quota()`; `tracking.py` and `reply_checker.py` are independent of both and of each other.

- **`base_sender.py`** owns everything that decides how a message looks to a spam filter — the text/plain + text/html multipart structure, `List-Unsubscribe`/`List-Unsubscribe-Post` headers, RFC `In-Reply-To`/`References` threading on follow-ups, the suppression-list check, and the copy generators (`generate_email`, `generate_followup`). This exists so the two transports can never silently drift apart on a deliverability-critical detail — see §8.
- **`ses_sender.py`** / **`gmail_sender.py`** are the only two files that know how to actually hand a built MIME message to a server. Selected via `emailer.get_sender()` (reads `config.EMAIL_PROVIDER`), which is the **only** construction point every caller (`app.py`, `main.py`, `send_approved.py`, `warmup_send.py`) is meant to use.
- **`tracking.py`** builds the open-tracking pixel and the ID that matches a pixel fetch back to a send — see §8 for why the resulting numbers are directional, not exact.
- **`reply_checker.py`** connects to `IMAP_USER`'s mailbox read-only and matches inbound mail back to a sent email — see §8 for why this is the one engagement signal actually worth trusting.
- **From vs Reply-To**: `config.REPLY_TO_EMAIL` (defaults to `FROM_EMAIL`) exists because the two have different jobs — see the `REPLY_TO_EMAIL` row in §4 and the `Reply-To` gotcha in §8.

## 7. Code Style Conventions

- Type hints used fairly consistently (`str | None`, `list[str]`, `dict | None`); `@dataclass` for structured results (e.g. `WebsiteData` in `scrapers/website.py:59`).
- Docstrings: Google-style `Args:`/`Returns:` blocks (`scrapers/website.py`, `analyzer/ai_audit.py`, `analyzer/lighthouse.py`).
- Error handling: broad `try/except Exception`, generally swallowed with `print(f"[Tag] ... error: {e}")` and a safe empty/False/`{}` fallback rather than raised. This is the dominant pattern — match it rather than introducing raised exceptions unless deliberately changing behavior.
- Logging is entirely `print()` with bracketed tags (`[Lighthouse]`, `[Audit]`, `[Parse]`, `[Axe]`, `[Links]`, `[PageSpeed API]`, `[Jina]`) — no `logging` module anywhere.
- Pattern: one class per scraper/auditor module (`WebsiteScraper`, `GoogleMapsScraper`, `InstagramScraper`, `AIAuditor`, `SESSender`, `SheetsStorage`, `DecisionMaker`), instantiated **once at module scope** in `app.py:50-56` and reused across requests — these hold long-lived clients (`httpx.AsyncClient`, API clients), not per-request instances. Don't instantiate per-request.
- Async/sync mixing: `scrapers/website.py` is async (`httpx.AsyncClient`). `analyzer/lighthouse.py` is `async def run_lighthouse` and, as of 2026-07-10, wraps its blocking `subprocess.run` helpers (`_run_lighthouse_cli`/`_run_lighthouse_npx`) in `asyncio.to_thread` — a 120s Lighthouse run no longer blocks the event loop. `storage/db.py` and `storage/sheets.py` are fully synchronous (`sqlite3`, `gspread`); `app.py`'s async route handlers wrap their direct sync calls (`db.*`, `ses.*`, `ig_scraper.*`, `decision_maker.*`) in `asyncio.to_thread(...)` so they no longer block the event loop — follow that pattern for new sync calls added to route handlers. `main.py` (CLI batch script) still calls these synchronously inline, which is fine there since it's single-threaded sequential processing with no concurrency to protect.
- Naming: snake_case in Python; camelCase in React state; snake_case DB columns. **Mismatch:** Google Sheet headers (`storage/sheets.py:19-39`) use human-readable Title Case strings as the actual field keys — different schema convention from the SQLite side.
- `@staticmethod` + `_`-prefix for private helpers not needing `self` (e.g. `scrapers/website.py:428,521,531`).

## 8. Known Gotchas / Fragile Areas

Most of the issues found in the 2026-07-10 audit were fixed the same day — see §13 Changelog for the full list (tuple-unpack bug, `main.py` hardcodes/dupe import, Lighthouse `output_path` guard, screenshot filename collisions, `init_db()` running its cleanup DELETE on every call instead of once, Crawl4AI/Wappalyzer being silent no-ops, dead files, and a second round: no API auth, a broken scheduler.py ingestion path, SSL verification disabled, bare excepts, unpinned dependencies). What's still true:

- **`/api/*` auth is opt-in, not enforced.** `require_api_key` (`app.py`) only checks `X-API-Key` if `config.API_KEY` is set — if you forget to set it, every route stays wide open (app.py prints a startup warning, but nothing blocks you from ignoring it and deploying anyway). Always set `API_KEY` before deploying anywhere internet-reachable, and keep `frontend`'s `VITE_API_KEY` in sync (baked into the frontend bundle at build time, so it's visible to anyone who reads the JS — fine for stopping casual/automated abuse of the raw API, not a substitute for real per-user auth if this ever becomes multi-tenant).
- **Playwright concurrency capped at 1** via global `asyncio.Semaphore(1)` (`analyzer/visuals.py:15`) to avoid OOM on Railway's 500MB instances — audits run serialized, not parallel. This is a deliberate resource constraint, not a bug; revisit only if upgrading the Railway plan or moving audits to a separate worker. This is also *why* Playwright navigation timeouts were kept (not removed entirely) when fixing the false-"website down" bug below — a truly unbounded wait on one bad site would freeze every other lead queued behind it through the single shared browser, not just fail the one lead.
- **Playwright navigation used `wait_until="load"`, which is much stricter than what "the site loads" actually means to a human** — `"load"` waits for every single resource (analytics beacons, chat widgets, ad iframes, web fonts) to finish, and on a lot of real small-business sites this never fires within any timeout even though the site is fine and renders instantly for a real visitor. Live-verified 2026-07-13: a site that curl'd back in 2.5s was being reported as fully "unreachable" (0/100 scores, a drafted "Your Website Is Down" email) purely because one hung third-party script kept `"load"` from ever firing. Fixed by switching every navigation in `analyzer/visuals.py` (homepage, extra pages, mobile revisit) to `wait_until="domcontentloaded"` (fires once the page itself is parsed and usable) with a more generous timeout kept as a safety net.
- **A second, different false-"website is down" bug, fixed 2026-08-07**: `scrapers/website.py:audit_website`'s `if not html:` branch (Playwright produced nothing after both retries in `analyzer/visuals.py`'s retry wrapper) used to assume that meant the site was actually unreachable, and that exact wording (`"Website is unreachable or returned an error"`) flowed straight into the AI prompt and out as "Your website isn't loading right now" in a real cold email. Live-verified against a real lead (`brandyaar.com`, a JS-heavy site with a full-screen homepage intro animation): the site audited completely cleanly on the very next attempt, meaning Playwright — not the site — was the thing that failed, most likely a bot-detection challenge or the loading screen simply outlasting the settle wait. **A headless-browser failure is not proof of an outage**, and this is exactly the same "confident wrong claim from a failed signal" bug class as the rest of this section — the fix follows the same shape as `partial_coverage` elsewhere: before letting the flaw claim "unreachable," `audit_website` now fires one plain `httpx` GET (no JS, none of Playwright's bot-fingerprinting surface) at the same URL. Only if *that* also fails does the flaw keep the "unreachable" wording; if it succeeds, the flaw instead says the audit couldn't fully render the page but the site itself responded normally, and `reachable` still correctly stays `False` (the technical audit genuinely didn't run) — only the *claim about why* changes. See `test_accuracy_guards.py`'s two `_FakeClientReachable`/`_FakeClientGenuinelyDown` tests. **A third round on the same day, same bug class, one level deeper**: even the softened "reachable but not auditable" wording got inflated by the AI into an unsupported causal claim — reported live on a different lead (`tubersstudio.com`, which re-audited completely cleanly, confirming the original failure was a one-off blip): "this barrier makes it harder for search engines to crawl and index your content." That's a real leap — our one headless-browser fingerprint getting blocked twice proves nothing about whether Googlebot is also blocked, and real bot-protection layers routinely allowlist known crawlers separately from generic automated tools. The flaw text now explicitly states "Do NOT claim or imply this affects search engine crawling, SEO, or Google indexing — we have no evidence of that" directly in the description the AI is instructed to quote from, and severity dropped `critical` → `low` (this is a gap in what we could measure this run, not a confirmed site defect, and `compute_score` treats severity as real evidence of a problem). Live-verified the AI's copy flipped from the false SEO-harm claim to the accurate opposite ("your SEO and indexing are totally fine"). See `test_accuracy_guards.py::test_playwright_failure_does_not_imply_an_seo_crawling_problem`. **Fourth and final round, on explicit user instruction: stop softening the wording and don't audit these leads at all.** After three rounds of narrowing what the flaw text is allowed to claim, the user's call was that no wording fix is good enough — if Playwright can't render the page, skip the lead entirely rather than draft anything from zero real audit data. `main.py:process_single_lead` and `app.py`'s `/api/audit` now both check `html_content` immediately after `generate_audit_screenshot()` and bail out (`"failed_unreachable"` status / `{"error": ...}` response) *before* calling `audit_website`, the AI, or `decision_maker` — `scrapers/website.py:audit_website`'s `if not html:` branch (and its httpx/SEO-claim guards above) is kept as a defensive fallback for any future/other caller, but is no longer reachable from either production entry point. See `test_accuracy_guards.py::test_audit_skips_entirely_when_playwright_cannot_access_the_site`.
- **The homepage settle delay was bumped from 2s to 10s the same day** (`analyzer/visuals.py`, same root cause as above) — a full-screen JS preloader/intro animation on the homepage can still be up when the old 2s delay expired, so axe-core and the screenshot could fire against the loading state instead of the real page. This is homepage-only (extra pages/mobile stayed at 1.5s) since preloaders are a first-impression pattern, not something a `/services` subpage typically repeats. Adds ~8s to every audit's wall-clock time — accepted deliberately, matching this file's whole history of trading speed for not shipping a wrong claim.
- **`main.py`'s skip-if-too-good check was a separate reimplementation of `AIAuditor.should_contact()`, not a call to it, and had silently drifted from it — fixed 2026-08-07.** `should_contact()` is the documented, tested single source of truth for the contact/skip decision (see `analyzer/ai_audit.py`, `test_accuracy_guards.py`), but was never actually called anywhere outside its own tests. `main.py` instead had its own inline `if analysis.get("overall_score", 100) > 70`, which disagreed with `should_contact()`'s `< 70` at the exact boundary — a score of precisely 70 was drafted by `main.py` but would have been treated as "too healthy, skip" by `should_contact()`. Low real-world odds of hitting exactly 70, but the larger risk was structural: a "single source of truth" that nothing actually reads through is one edit away from silently diverging further. `main.py` now calls `auditor.should_contact(analysis)` directly.
- **The red-box element's `bounding_box()` call used a 1s timeout, an outlier against every other wait in the same function** (bumped to 3s, 2026-08-07, `analyzer/visuals.py`) — the homepage settle delay above it went from 2s to 10s the same day for the same underlying reason (a late-rendering/animating element needs more than a blink to become measurable), and this was the one wait in `_run_axe_audit` that was never revisited when the rest of the function's timeouts were generously bumped. Not independently live-verified to have caused a missed box (unlike the viewport-bounds bug above, which was live-reproduced) — a low-risk, plausible-but-unconfirmed improvement in the same spirit as the temperature change documented elsewhere in this file.
- **`_AUDIT_SCREENSHOT_RETRIES` raised from 2 to 3, 2026-08-07** (`analyzer/visuals.py`) — the `brandyaar.com` false-"down" incident this same day hit exactly two failures in a row before the httpx fallback caught it; a third attempt costs one more ~5s retry delay on an already-rare failure path and further reduces how often a lead needs the fallback wording at all.
- **`review_warnings` is now surfaced in the Drafts UI, not just server logs** (2026-08-07 — see §5.5/§9). If a draft shows a red "Review before sending" banner, read it before approving: it means the hallucination check, the source-quote check, the LLM grounding judge, the spam-word scan, or the body-length check flagged something specific about that exact email. None of these five checks block or auto-fix a send — they only got a visible home; a draft with no banner has passed all five, not been guaranteed perfect (see each check's own false-positive/negative caveats already documented in `analyzer/ai_audit.py`).
- **`WARMUP_ENABLED` (added 2026-08-07) only does anything if `scheduler.py` runs as its own Railway service — setting the env var alone changes nothing on the existing web service.** See the new §12 entry: `app.py`'s Dockerfile `CMD` never invokes `scheduler.py`, so this and every other cron in that file (batch sends, follow-ups, lead ingestion) needs that second service deployed before any of it fires automatically. `warmup_send.py`'s recipients file also needs to live in the persistent `/app/data` volume in production (`data/warmup_recipients.txt`), not the repo-root path used for local dev — `_load_recipients()` checks both, in that order.
- **The red-box coordinate pipeline didn't check whether the box was actually inside the captured screenshot, fixed 2026-08-07.** `page.locator(selector).bounding_box()` reports position in full-*document* coordinates, not clipped to the viewport — an element below the fold (a footer iframe, a widget halfway down the page) still returns a "valid" non-null box, but `page.screenshot(full_page=False)` only captures the viewport. Live-verified against a real lead (`lp.zooty.in/anjaneya-dental-care`): a `frame-title` violation on an off-screen iframe produced a box at `y=4858` on an 800px-tall image — invisible, off-canvas, while the code still generated red-box text for the email claiming one was there. A second run on the same site picked a full hero wrapper `<div>` instead — in-bounds at the top, but tall enough to fill nearly the whole visible screenshot, which reads as "the whole page is highlighted" rather than a specific flaw; the pre-existing "skip if >90% of screen" guard didn't catch it because it required **both** width and height to be near-full (an AND), so a merely-tall-but-not-quite-1150px-wide wrapper sailed through. `_run_axe_audit` (`analyzer/visuals.py`) now rejects any candidate box not fully contained within the actual viewport (read from `page.viewport_size`, not hardcoded, since mobile passes use a different one) before falling through to the next node/violation — on the reported site this now correctly picks a small `color-contrast` violation on a nav item instead.
- **The prompt used to MANDATE a visual critique on every single email, which is a hallucination generator by construction — fixed 2026-08-09.** `_build_prompt` (`analyzer/ai_audit.py`) carried an unconditional `"CRITICAL INSTRUCTION FOR FLAWS: ... ONE OF YOUR FLAWS MUST BE A VISUAL CRITIQUE"` whenever a screenshot was attached, i.e. essentially always. A site with genuinely clean design left the model no honest way to comply, so it invented a criticism — and this is the **highest-risk claim type in the whole email**, because the recipient is looking at their own site while reading it. It also directly contradicted the `source_quote` rule in the same prompt (*"if you cannot copy an exact line for this claim, do not make the claim at all"*), since a typography/alignment observation usually has no matching line in `FLAWS DETECTED`; the model had to break one instruction or the other. A side effect worth knowing: under the old prompt nearly every draft tripped `_verify_source_quotes`, which turned a real deterministic signal into constant noise — narrowing the demand makes that warning meaningful again. The demand now only appears when `_has_visual_evidence(web)` is true (a red box was actually drawn, or the font-consistency / stretched-image check actually fired — matched on flaw *description*, since both are filed under the broad `"content"` category alongside non-visual flaws like favicon/thin-content). With no evidence, the prompt explicitly says *"Do NOT invent a visual criticism to fill a quota — a clean design is a perfectly normal result."* See `test_visual_claims.py`.
- **Visual claims were the one claim type nothing could verify, until `_verify_visual_claims` (added 2026-08-09).** `_verify_source_quotes` has no `FLAWS DETECTED` line to match a design observation against, and `_verify_grounding` sends the judge `prompt[:6000]` — **text only, the image is never in view** — so it was being asked whether "the fonts in your hero and nav don't match" is supported by source data containing zero visual information. It could only guess, in either direction. `_verify_visual_claims` routes only visual-sounding claims (`_VISUAL_CLAIM_KEYWORDS`) plus the real screenshot to `_call_vision_judge` and asks whether each is actually visible. **Non-visual claims must never be routed there** — a load time isn't visible in a screenshot, so it would come back "unsupported" every time and drown the real signal. Same contract as every other check: never blocks a send, degrades to `None` if no vision provider is configured, feeds `review_warnings`. Costs one extra image-carrying LLM call per lead *that makes a visual claim* — after the fix above, that's no longer every lead.
- **`review_warnings` had no teeth until 2026-08-09 — a flagged draft was one click from going out.** The six checks have flagged suspect copy since 2026-08-07 and the Drafts UI has shown a red banner since then, but `/api/send` never read the column, so the entire safety net came down to whether a human happened to read the banner before clicking. It now looks the draft up (`db.get_draft_by_website`) and returns `409` listing the specific blockers unless `acknowledge_warnings: true` is set. **`SendRequest.acknowledge_warnings` defaults to `False` deliberately so the gate fails closed** — a caller that doesn't know about the check (a script, an older frontend bundle) can't bypass it by omitting the field. The same `409` also covers draft staleness: audit data is frozen at generation time while the draft sits in the inbox indefinitely, so past `DRAFT_STALE_DAYS` (default 7) the site may have been redesigned or fixed and the email would still cite the old findings as current fact. An **unparseable** draft timestamp deliberately does *not* block the send — that's a data problem, not a reason to refuse otherwise-clean copy — and a send with no matching draft row (the audit view sends directly, never saving a draft) passes through untouched.

- **Reply detection (`emailer/reply_checker.py`) is read-only by design, and the auto-reply/bounce split is the whole point.** The scanned mailbox is a human's real inbox, so it connects with `select(readonly=True)` and fetches with `BODY.PEEK[HEADER.FIELDS ...]` — marking someone's mail as read as a side effect of a background poll would be its own bug, and only headers are pulled (enough to identify and match a reply, not enough to display its text). **An out-of-office or a bounce must never count as a reply**: an autoresponder proves the address is live, not that a human read anything, and folding either into the reply count would corrupt the one metric here that's meant to be exact. Matching is threading-headers-first (`In-Reply-To`, then `References`) with a **fallback to the sender's address**, because plenty of clients drop threading headers entirely and losing a real reply is worse than the small chance of crediting the wrong send. A real reply outranks an earlier auto-reply on the same thread. **Bounces are counted but never auto-suppressed** — identifying *which* address failed requires the delivery-status part of the body, which isn't fetched, so suppressing on a guess could permanently block a real lead. Re-scanning is idempotent (`email_replies` PK is the reply's own Message-ID; replies lacking one get a content-derived synthetic key), which matters because the default 30-day window means every scan re-reads the same replies.

Uses `scan_type="fast"` (single HTTP request, no browser) — live-tested at ~5s against wordpress.org, correctly detected WordPress/PHP/MySQL/Nginx/etc. Still runs off-thread via `asyncio.to_thread` with a 10s outer timeout, degrading to `[]` on timeout/error. **Do not install both `python-Wappalyzer` and `wappalyzer` in the same environment**: on case-insensitive filesystems (Windows, default macOS) their package directories (`Wappalyzer/` vs `wappalyzer/`) collide and corrupt both installs — hit this firsthand during this session, confirmed by uninstalling both and reinstalling `wappalyzer` alone. `requirements.txt` only lists the new one, so a fresh `pip install -r requirements.txt` is fine; this only bites if you `pip install python-Wappalyzer` back in manually.
- **`pyseoanalyzer` makes its own separate HTTP fetch of the target URL** (not the Playwright HTML already in hand) — accepted tradeoff (see §5.6) for real crawl-based checks (word count, page warnings). Adds a few seconds to each audit; `follow_links=False` keeps it to just the one page. Its extracted `description` field can occasionally pick up garbage (live-tested on a messy real site, it once flagged a video file URL as "the description is too long") — surfaced as-is in the flaw list since filtering every possible garbage pattern isn't worth the complexity; treat pyseoanalyzer warnings as generally useful but not 100% clean signal. Its "Anchor missing title tag" and "Image missing alt tag" warnings are both filtered out entirely (`scrapers/website.py`) — the former fires on nearly every anchor on most sites (not a meaningful signal), the latter live-verified to fire on `alt=""` images (the *correct* WCAG pattern for decorative images, contradicted by axe-core which correctly didn't flag them).
- **`_check_font_consistency` (`analyzer/visuals.py`) only counts visually-relevant text elements.** Skips elements with no visible text (empty headings, icon-only buttons), `sr-only`/`screen-reader`/`visually-hidden` classes (skip-links etc.), and near-zero (`<=2px`) bounding boxes — before this filtering, an icon-only search button's `Arial` fallback font was counting as a real font on the page. If a font-count flaw looks wrong, check whether the source element is actually visible to a sighted user, not just present in the DOM.
- **`_check_broken_assets` (`analyzer/visuals.py`) retries via GET before trusting a HEAD failure.** Some servers/WAFs selectively reject or rate-limit HEAD requests from automated tools while GET succeeds for the same asset — live-observed this exact flakiness (same site, same code, different runs: 6 "broken" links vs 0). Only a failure on *both* HEAD and the GET retry is reported as broken.
- **Two storage backends, two schemas**: SQLite (`storage/db.py`, snake_case columns) and Google Sheets (`storage/sheets.py`, Title Case header strings as field keys) are separate, unreconciled data stores — Sheets is the lead/CRM source of truth (`get_pending_leads`, `find_row_by_website`, etc.), SQLite is cost/history/drafts only. Not touched in this pass; if scope grows, decide whether to retire one (e.g. Baserow, MIT-licensed self-hosted Airtable alternative, was considered but not implemented — needs a deployed instance first).
- **Rate limiting** is in place on all `/api/*` routes (`app.py:rate_limit`, in-memory sliding window keyed by API key, `429` on breach): 5/min on `/api/search` and `/api/audit`, 10/min on `/api/send`, 30/min on the drafts delete, 120/min on the three GET/poll endpoints (`/api/costs` is polled every 5s by the frontend, so it needs headroom). In-memory only — fine for one Railway instance, won't hold up if this ever runs multi-instance/multi-worker (would need Redis or similar for a shared counter).
- **`validate_email(..., check_deliverability=True)` (`enrichment/decision_maker.py`) is unreliable from a cloud host** — DNS/MX lookups get blocked or time out often enough that a real, scraped-off-the-site email can fail the check and incorrectly get discarded, cascading down to the much weaker OSINT-guess strategy. Fixed 2026-07-10: `_scrape_website_for_email` now falls back to accepting the top-scored candidate on format validity alone (`check_deliverability=False`) if every candidate fails the deliverability probe, instead of returning `""` and falling through. Also added `_is_junk_email()` — filters `noreply@`/`no-reply@`/`postmaster@`/etc. out of both the scraper and the OSINT dork fallback (`_find_email_via_osint`), since those matched too easily off random search-snippet text and produced nonsense "To" addresses in drafted emails.
- **Contact name defaults to a generic `"{company_name} Team"`, not a fixed string.** Used to be hardcoded `"Marketing Team"`/`"Team"` across all three no-real-name-found code paths in `find_decision_maker` — every cold email opened with the same generic "Hi Marketing Team," regardless of which business it was for. Fixed 2026-07-10.
- **Audit screenshots are taken right after Playwright's `load` event fires, which is often too early** — CSS fade-in animations, lazy-loaded hero images, and cookie-consent widgets aren't done rendering yet, so the captured screenshot can look faded/broken and not match what a real visitor sees. Fixed 2026-07-10 (`analyzer/visuals.py:generate_audit_screenshot`): best-effort `wait_for_load_state("networkidle", timeout=5000)` + a fixed 1s settle delay before capturing, wrapped so a slow/never-idle page (e.g. persistent chat-widget polling) doesn't fail the whole audit.
- **Instagram scraping (`instagrapi`) and the Google Maps Playwright fallback both scrape platforms directly against their ToS.** This session added mitigations, not a fix — the underlying ToS/ban risk doesn't go away:
  - `scrapers/instagram.py`: added a circuit breaker (`_trip_challenge_breaker`) — a `ChallengeRequired` from Instagram now pauses *all* Instagram calls for 60 minutes (`_CHALLENGE_COOLDOWN_SECONDS`) instead of retrying immediately, which is what turns a soft flag into a permanent ban. `_ensure_logged_in` checks the cooldown before attempting any login.
  - `scrapers/google_maps.py`: jittered delays (was fixed `sleep(1.5)`/`sleep(3)`, now randomized ranges) on the Maps scroll loop, plus a jittered delay + `asyncio.to_thread` between each DDG website-lookup call (was a tight zero-delay loop hammering DDG synchronously on the event loop).
  - A dedicated scraper repo (e.g. gosom/google-maps-scraper) was considered for the Maps side but skipped — it's written in Go, not Python, bigger integration than warranted right now.
- **`import app` performs a real, live Google Sheets authentication call at module-import time** (`app.py`: `sheets = SheetsStorage()` at module scope → `storage/sheets.py:__init__` → `gc.open_by_key(...)`, which mints a fresh service-account JWT on first use). **The practical consequence: every test that does `import app` (most of `test_accuracy_guards.py`, `test_open_tracking.py`) is coupled to live Google Sheets connectivity succeeding at collection time**, so an unrelated environment problem shows up as scattered test failures across multiple files, not a clearly-labeled Sheets error. Live-verified 2026-08-07: this broke a batch of already-passing `TestClient` tests with `google.auth.exceptions.RefreshError: invalid_grant ... Token must be a short-lived token`. Root cause, confirmed (not just suspected): **the dev machine's system clock had drifted 11 days into the future** (read 2026-07-28 when the real date was 2026-08-09) — Google's OAuth server rejects any JWT whose `iat` is that far from real time, which is exactly this error. Nothing wrong with the credentials file or the code; correcting the Windows clock fixed it immediately with no other changes, confirmed via `python -c "import gspread; gspread.service_account(filename='credentials.json').open_by_key('<GOOGLE_SHEETS_ID>')"` and then a full clean test run. If a batch of otherwise-unrelated `app`-importing tests suddenly fail together with a `google.auth` error, check the system clock before suspecting the credentials or the code under test.

## 9. Database Schema (`storage/db.py`)

SQLite at `data/database.sqlite` (repo-root-relative, auto-created). Every public function (`log_cost`, `log_email`, `get_costs`, etc.) calls `init_db()` and opens/closes its own `sqlite3.connect()` — no shared connection or pool.

- **`cost_logs`**: `id` (PK autoincrement), `timestamp` (default `CURRENT_TIMESTAMP`), `category` (TEXT NOT NULL — e.g. `"Google Maps API"`, `"AI Audit"`, `"AWS SES"`, `"AI Web Fetch"`), `cost` (REAL NOT NULL), `description` (TEXT)
- **`email_history`**: `id` (PK), `timestamp`, `company`, `website`, `target_email`, `sender_email`, `subject`, `body`, `message_id` (added via `PRAGMA user_version` migration — RFC threading against the SES `Message-ID`, see §8)
- **`email_drafts`**: `id` (PK), `timestamp`, `company`, `website`, `target_email`, `subject`, `body`, `image_url`, `review_warnings` (added via `PRAGMA user_version` migration, schema v5 — JSON-encoded list of strings from `AIAuditor`'s six accuracy checks, `NULL`/empty when none fired; `db.get_drafts()` decodes it back to a list, defaulting to `[]` on `NULL` or malformed JSON, see §5.5/§8). Since 2026-08-09 this column also has teeth: `db.get_draft_by_website()` reads it (and the row's `timestamp`) on the send path so `/api/send` can `409` a flagged or stale draft rather than only displaying a banner.
- **`email_opens`**: `id` (PK), `tracking_id` (indexed), `timestamp`, `user_agent` (truncated to 300 chars), `ip_hash` (blake2s digest, not the address), `is_automated` — **one row per pixel fetch, not per email**. Collapsing to a boolean at write time would throw away the repeat-open signal, so aggregation happens at read time in `get_open_summary()`. No FK to `email_history`: rows are matched by a digest of the `Message-ID` (see §8), and a hit can legitimately arrive for a message this database never recorded.
- **`email_replies`**: `reply_message_id` (PK — the *reply's* own Message-ID, so re-scanning the mailbox is a no-op rather than a pile of duplicates; a reply without one gets a content-derived synthetic key), `timestamp`, `in_reply_to` (indexed), `from_email`, `target_email` (indexed), `subject`, `is_auto`, `is_bounce`
- **`email_suppressions`**: `email` (PK), `timestamp`, `reason` — checked before every send (`SESSender.send_email`/`send_followup`), populated by the public `/unsubscribe` route (RFC 8058 one-click)

Rows are converted `sqlite3.Row` → `dict(row)` for JSON-serializable API responses.

## 10. Frontend Architecture (`frontend/`)

- Single-page app, **no router library** — view switching via `useState('home')`/`currentView` string with conditional rendering in one large component (`frontend/src/App.jsx:9-10`).
- **No global state library** — plain `useState`/`useRef`/`useEffect`. `leads` state persists to `localStorage` under key `leadAuditLeads` (`App.jsx:14-17,49-51`).
- **No dedicated API service layer** — `axios` calls are made directly inside component handlers. `API_BASE = ""` (relative paths, same-origin) at `App.jsx:7`.
- Polls `/api/costs` every 5s via `setInterval` for a live running-cost pill (`App.jsx:68-75`).
- **Both send paths go through `sendWithAcknowledgement()`** (added 2026-08-09), which treats a `409` from `/api/send` as a deliberate stop rather than an error: it shows the human the exact blockers (review warnings and/or a staleness notice) in a `window.confirm` and only retries with `acknowledge_warnings: true` if they agree. It returns `null` when they decline, so callers must not treat that as a successful send — the draft stays in the list and the lead's state reverts. Draft cards also show an amber "drafted N days ago" badge mirroring the server-side `DRAFT_STALE_DAYS` gate. See §5.1/§8.
- "Autopilot" mode sequentially calls `/api/audit` per lead, using refs (`isAutopilotRef`, `leadsRef`) to avoid stale closures inside the loop (`App.jsx:141-150`).
- Build: `vite build` → `frontend/dist/`. `dist` is gitignored and (as of 2026-07-10) untracked — Docker builds it fresh on every Railway deploy (see §12); `app.py:252-254` mounts it as static files at `/` if present.
- Lint: `oxlint` (not ESLint) — config at `frontend/.oxlintrc.json`, run via `npm run lint` in `frontend/`.
- `frontend/vite.config.js` is the unmodified default Vite React template (no aliasing/proxy/env config).
- `frontend/README.md` is stock Vite+React boilerplate — no project-specific content, ignore it.

## 12. Deployment (Railway)

Railway builds from **`Dockerfile`** (`railway.json` pins `"builder": "DOCKERFILE"`). The repo used to also carry a leftover, unused `nixpacks.toml` from an earlier setup — deleted 2026-07-10.

- `Dockerfile` is a 3-stage build: a Python deps stage, a Node `frontend-builder` stage that runs `npm run build` fresh on every deploy, and a final Python+Playwright+Node runtime image that copies both in. Playwright's Chromium system deps (`libnss3`, `libatk1.0-0`, etc.) are installed via `apt-get` in the final stage; `playwright install chromium` downloads the browser itself.
- **The final runtime stage now installs Node.js + runs `npm install` for the root `package.json`.** Fixed 2026-07-10 — before this, the final stage was plain `python:3.11-slim` with no Node at all, so `analyzer/lighthouse.py`'s check for the `lighthouse` binary always failed silently on every single deploy, falling through to the PageSpeed API fallback (which was also failing, likely `PAGESPEED_KEY` never added as a Railway variable) — real-world symptom was every audit showing `0/100` for both performance and SEO, live-verified as a Lighthouse/Node availability bug, not a timeout (`_execute_lighthouse` already has a generous 120s subprocess timeout). Verified locally (Windows can't exec the `.bin` symlink directly, `WinError 193`, but invoking `node node_modules/lighthouse/cli/index.js` directly against a real site produced correct scores) — the underlying `npm install` + Lighthouse package wiring is confirmed correct; the fix works on Linux (Docker) where the `.bin` symlink executes fine.
- `_pagespeed()` (`scrapers/website.py`) now logs *why* it failed instead of silently returning `{}` — explicit warning if `PAGESPEED_KEY` is unset, logs the raw response keys if `lighthouseResult.categories` is missing, and includes the response body in the exception log.
- **`frontend/dist/` is no longer committed to git** (untracked 2026-07-10 — it used to be, which meant a locally-built bundle with a baked-in `VITE_API_KEY` could end up in git history). The Docker build produces it fresh from `frontend/` source every deploy; `app.py` mounts it if present, same as before.
- **Set `VITE_API_KEY` as a Railway *Build Variable*** (not just a regular deploy-time env var — it needs to be visible during the Docker build, since that's when `npm run build` bakes it into the JS). The `Dockerfile`'s `frontend-builder` stage declares `ARG VITE_API_KEY` to receive it. Without this, the deployed frontend won't send `X-API-Key` and every request will 401 once `API_KEY` is set server-side.
- Railway mounts a persistent volume at `/app/data` to ensure `database.sqlite` and `screenshots/` survive deployments.
- **The Gmail transport and reply detection need no Dockerfile changes.** `smtplib`/`imaplib` are Python stdlib — unlike Lighthouse/html-validate/pa11y, there's no Node binary or system dependency to install for `EMAIL_PROVIDER=gmail` or `/api/check-replies` to work; setting the relevant env vars in Railway (see §4) is sufficient on its own.
- **`scheduler.py` is NOT run by the deployed web service, confirmed 2026-08-07.** The `Dockerfile`'s only `CMD` is `uvicorn app:app` — nothing in `Dockerfile`/`railway.json` references `scheduler.py`. This means the Mon-Fri 10am sends, 9am follow-ups, Sunday 8pm lead ingestion, and the warm-up job (`WARMUP_ENABLED`) documented elsewhere in this file **do not run automatically in production unless `scheduler.py` has separately been deployed as its own Railway service** (`railway up`/a second service in the same project pointed at this repo with start command `python scheduler.py`, needing the same env vars as the web service). If that second service was never created, every cron in this file is dormant and the only way anything gets sent is a human manually running `main.py`/`warmup_send.py`, or using the dashboard's Autopilot. Verify via Railway's dashboard whether a second service exists before assuming any of this file's documented schedules are actually firing.
